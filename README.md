# creator-analytics

Stillstats: privacy-first YouTube analytics for creators.

Read `CONTEXT.md` for the language and `docs/adr/` for the decisions. This file holds the product brief that is not an ADR, from the grilling session of 2026-10-03.

## Who it is for

Small creators who manage one channel, with Nick as the first user. Agencies that manage many channels are a second market, served later through the agency workspace.

## Why it exists

A tool Nick needs, with revenue a close second, and build-in-public content for the channel as a free result. The incumbents (vidIQ, ViewStats, TubeBuddy, Social Blade and others) monetize creator data and still sell metrics that no longer matter. The research behind this is in the Knowsmore vault at `content/channel/research/sources/2026-10-03-creator-analytics-tools-data-practices.md`.

## Version 1 scope

Own-channel analytics only (ADR 0004). Metrics in: engaged views, views, retention, traffic sources, countries, subscribers gained per video. Retired metrics are listed in ADR 0009.

Three metrics are out of version 1. The YouTube Analytics API returns no CTR and no impressions: only the Reporting API does, as daily files that need stored history, which ADR 0006 allows on Stillstats Pro only, so they arrive with Stillstats Pro. No YouTube API returns returning and new viewers, so the subscriber split stands in for them, labelled as exactly that.

## Pricing (working)

- Free tier: current analytics for the creator's own channel, including engaged views. No stored history.
- Studio extension: free, and shows free tier numbers only.
- Stillstats Pro: $7 a month or $70 a year for each block of 4 channels, for CTR and impressions history, and later outlier scores.
- Agency: per-channel pricing, later.

Competitor range on 2026-10-03: Morningfame from $3.90, TubeBuddy from $12, vidIQ from $19, ViewStats from $49.99 a month.

## Build order

Each spec is one epic, and each one's output is the input to the next:

1. Foundation: accounts and memberships, token vault, YouTube gateway, retention engine, and the stack choice.
2. Web PoC: private product API, web app, self-hosted product analytics.
3. Marketing site and compliance: product name and domain, homepage, pricing, principles page, privacy policy, OAuth verification submission. Runs alongside the web PoC.
4. Studio extension.
5. Stillstats Pro: report job runner, entitlements and billing.
6. Compliance audit application.
7. Agency workspace and export workbook.
8. Outlier engine, after acceptance under the derived-metrics policy.

## Platform facts that shape the build

- The YouTube APIs carry no monetary charge; the limit is quota. The Data API default is 10,000 units a day plus 100 `search.list` calls. More quota needs the compliance audit, which has no fee.
- OAuth verification needs a homepage on a verified domain the product owns, with a privacy policy linked from it. No YouTube scope is restricted, so no CASA assessment applies. Unverified apps are capped at 100 users.
- YouTube deletes Reporting API files after 60 days, and the Analytics API does not return impressions or CTR, so paid history needs a daily report job.
- In-app revocation requires deletion within 7 days; revocation through Google's security settings, within 30.

The API reads `STILLSTATS_ENVIRONMENT`, `DATABASE_URL`, `BETTER_AUTH_URL` (the origin it serves), `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `TOKEN_ENCRYPTION_KEYS` and `GOOGLE_IDENTIFIER_KEY`. `STILLSTATS_ENVIRONMENT` is `production` or `staging`, and the API and the worker refuse to start with it unset or set to anything else. On `staging` the API also reads `CLOUDFLARE_ACCESS_TEAM_DOMAIN` and `CLOUDFLARE_ACCESS_AUD`, refuses to start without either, and answers 403 to any request without a valid Cloudflare Access token in `Cf-Access-Jwt-Assertion` (`docs/deploy.md`, Staging); on `production` it reads neither. Sign-in uses Better Auth's generic OAuth plugin, not its Google provider, so tests can point it at the fake Google server in `packages/fake-google` (#10 records why).

Sign-in and the connection use the same Google OAuth client, with two redirect URIs to register:

- `<BETTER_AUTH_URL>/api/auth/callback/google` for sign-in.
- `<BETTER_AUTH_URL>/api/channels/connect/callback` for the connection.

A sign-in or a connect begun on the upgrade screen's address, `/app/upgrade`, lands back there (#907). The web app's signed-out screen there signs in with `POST /api/auth/sign-in/google?then=connect&landing=upgrade`, and its empty state connects with `POST /api/channels/connect?landing=upgrade`. A sign-in by a user who holds a channel lands on `/app/upgrade`, which opens for the first channel. A first visit, and a connect from the empty state, land on `/app/upgrade?channel=<id>&connected=1`, the channel just connected, and a refused one on `/app/upgrade?connect_error=<refusal>`. A sign-in Google refuses or the creator cancels lands on `/app/upgrade?error=<Google's code>`, through the sign-in's `errorCallbackURL`, which Better Auth keeps in its sign-in state; a sign-in with no landing names none, and lands on `/app?error=<code>`, Better Auth's `errorURL`. The connect keeps its landing in its consent state (`consent_states.landing`, migration 0036), so it survives the round trip through Google. `landing` is a name from a fixed set, `upgrade` alone, never an address: the API maps it to its own path, and any other value lands where none does, so no value of it sends the browser off the web app.

Revenue consent is a second consent step for a connected channel, never part of the connection. It asks Google for `yt-analytics-monetary.readonly`, plus the `openid` and `email` that Cross-Account Protection needs, through incremental authorization (`include_granted_scopes=true`), and returns through the connection's redirect URI, so it needs no URI of its own. The connect consent sends `include_granted_scopes=true` as well, so a reconnect keeps revenue consent and its grant time. The first visit's connect consent, right after sign-in, sends Google `login_hint` with the session's email and `prompt=consent`, so Google skips its account chooser. A connect started from Settings or the empty state, and the revenue consent, send no `login_hint` and `prompt=select_account consent`, so Google shows its account chooser and the creator can pick a channel under another Google account. A sign-in from the web app's signed-out screen, which carries the connection consent text, asks for the first-visit hop (`POST /api/auth/sign-in/google?then=connect`) and returns through `GET /api/channels/connect/after-sign-in`: a user who holds no channel goes straight on to the connect consent, with no click, and any other lands on the web app. A sign-in from the homepage or the tool page, neither of which carries consent text, lands on the web app. A cancelled or refused connect lands on the web app's empty state, which starts a consent only on a click. Google keeps a grant per Google account, not per channel, so the token vault records the revenue scope from a connect only when the connection already held it. The token vault records each scope with the time it was granted. A revenue consent where the creator picks another channel on Google's screen is refused with `channel_mismatch` and changes nothing, and a revenue read for a channel without revenue consent is refused with `consent_missing` before any Google call. Google answers a revenue read for a channel outside the YouTube Partner Program with zeros as often as with a 403 (Nick's walk of 2026-10-10). The gateway turns a 403 into `not_monetized` and caches it for 6 hours like an answer, so the next read after the cache asks Google again and a channel that joins the program shows revenue with no new consent. The token vault keeps the revenue scope, and the channel summary still answers its other numbers. The video list and a video's detail read each video's own revenue under the same consent and answer the same way: the list's rows carry their revenue and its ad and YouTube Premium sources, the detail its revenue sources and its revenue by day, or the answer says `consent_missing` or `not_monetized` in place of revenue. The list also says when Google answered no upload a revenue row over the window (its `revenue` with `reported: false`), and the web app then shows the no-revenue note in place of $0.00, as it does for `not_monetized`. A list sorted by revenue or one of its sources without revenue consent is refused with `consent_missing`. Every revenue read sends Google's `currency` parameter with the creator's saved currency, USD by default, and Google converts at its daily exchange rate; each currency keeps its own cache entry. The web app sends three more events for it: `give_revenue_consent_clicked`, `revenue_consent_given`, and `revenue_consent_refused` with the refusal code.

The job worker (`apps/worker`, `pnpm --filter @creator-analytics/worker start`) reads `STILLSTATS_ENVIRONMENT`, `DATABASE_URL` and `DELETION_LOG_KEY`, the HMAC key the deletion log hashes YouTube channel ids with. Generate it with `openssl rand -base64 32`, and never change it: a new key makes "was this channel deleted?" unanswerable for every earlier entry. The worker is the only process that runs pg-boss's maintenance and its cron pass, which sends each scheduled job. For the daily active user count the worker also reads `OPENPANEL_API_URL`, `OPENPANEL_CLIENT_ID` and `OPENPANEL_CLIENT_SECRET`, the same values as the API's, all three or none. With none, the job still counts and prunes, sends nothing, and reports "The active user count was not sent: OpenPanel is not configured" to GlitchTip on every run, with the counted day and no count. It does not fail, because a retry cannot fix a missing setting. For a paid channel's deletion the worker reads `STRIPE_SECRET_KEY`, a secret key, `sk_...`, or a restricted key, `rk_...`, with write on Subscriptions and Refunds and read on Invoices. A key that starts with neither stops the worker at start. With none, a paid channel's deletion still deletes its rows, and its cancellation fails on every run until the deletion's alarm reports it.

An activity day is the record that a user read a channel's numbers on a UTC day, one row per user and day (`activity_days`, migration 0023). It holds the user and the day and nothing else. A signed-in read of the video list, a video's detail, its sponsor report, the channel summary or the audience inserts it in the user's own scope, and only the system scope reads and deletes it. Each day at 00:15 UTC the `activeUserCount` job counts the active users of the UTC day that just ended, the counted day D: `dau`, the distinct users with an activity day on D, `wau` in the 7 days ending on D, and `mau` in the 30 days ending on D. It then deletes every activity day older than D-28, since the next day's 30 days start at D-28, so no row lives past 30 days while the count's send lands. The rows older than D-29 are deleted first, in their own transaction, so while OpenPanel refuses the send a row lives at most a day more. The row cascades from its user, so "Delete me" removes it. A day with no run is a gap in the chart, with no backfill.

Google revokes a grant in ways a security event may never report, so the revocation backstop (#16) finds the rest. A gateway read whose token refresh Google refuses with `invalid_grant` is refused with `connection_revoked`, and the same transaction marks the connection revoked and requests the channel's deletion as `google_revocation`. Each day at 04:00 UTC the `probeRoster` job reads the active connections through the `connection_roster` function (migration 0011) and enqueues one `probeConnection` job per channel, throttled with a pg-boss `singletonKey` to one per channel per UTC day. A probe is a token refresh, which spends no YouTube quota, and an `invalid_grant` ends the connection the same way. For the probe the worker also reads `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `TOKEN_ENCRYPTION_KEYS`, the same values as the API's. The function runs as `app_roster`, a role created by the migrations without `LOGIN` that no login role is a member of. It holds SELECT on the roster columns only, so the system scope reads each active connection's channel id, Google subject HMAC and connection time, and never a token.

Every connected channel gets a YouTube Reporting API job for its daily reach report, `channel_reach_combined_a1` (#779). Connecting a channel enqueues an `ensureReportingJob` job in the connect's transaction, and each day at 04:30 UTC the `reportingJobRoster` job enqueues one per active connection through the `connection_roster` function, throttled to one per channel per UTC day. The job runs in the channel's scope: the gateway stores a job Google already holds, or creates one, and records the job's id and creation time in `reporting_jobs` (migration 0029). The worker's gateway takes its Google authority from `createConnectionAuthority`, built from the probe's three values, so the worker reads no new setting. A channel still without a job 24 hours after it connected is reported to GlitchTip on every run until it has one. The same job then downloads a paid channel's reach history (#783): every report created after the newest one stored, or on a first subscription every one Google still holds (up to 60 days), each read by its header row and reduced to one row per video, day and traffic source type in `reach_history`, with each delivered day and its report's creation time in `reach_history_days` (migration 0031). A report for a day already stored replaces that day. A free channel downloads nothing. A failed download stops the run, and the next day's run resumes from the newest stored report; a paid channel whose downloads have failed for 3 days is reported to GlitchTip on every run until one succeeds. The daily connection probe already reaches every active connection whatever its tier, so it is the check that a paid channel's grant is still authorized (Developer Policies III.E.4.b).

The history of a video deleted on YouTube is deleted at the next daily check (#786, Developer Policies III.E.4.b, which asks for the check every 30 days). Each day at 05:00 UTC the `deletedVideoCheckRoster` job enqueues a `deletedVideoCheck` job per active connection, throttled to one per channel per UTC day. In the channel's scope, the check asks the Data API's `videos.list` (part `id`, 1 unit per 50 ids, uncached) which of the videos in the channel's `reach_history` and `retention_curve_reads` still exist, and deletes the history, the `retention_curves` points and the `retention_curve_reads` row of every video Google does not answer. Private and unlisted videos are answered, so they keep their history and their curves. The days in `reach_history_days` stay, so the history's start and the download cursor do not move. A channel with no history and no curve makes no call. A failed check deletes nothing, is reported to GlitchTip on every run (except for a revoked connection, whose channel is being deleted), and runs again the next day.

A paid channel's audience retention curves are stored (#950). Each day at 09:00 UTC, after Google's quota day turns at midnight Pacific, the `retentionCurveRoster` job enqueues a `retentionCurveRefresh` job per active connection, throttled to one per channel per UTC day. In the channel's scope, a paid channel reads its uploads, then the gateway's `audienceRetention` read (one Analytics query, over the video's lifetime: from its publish day to today) of the due videos, up to one read for each video under 28 days old and a 30th of the older ones, and never fewer than 100 a run. So a backfill spreads across days (a channel of 390 uploads fills in 4), and each older video is read again within its month however many the channel holds. Due, in this order: a video under 28 days old whose last read was on an earlier UTC day; a video never read, newest publish first; a video 28 days old or more whose last read is 30 days old or more, oldest read first. A scheduled or unpublished video is not read; a private or unlisted one is. Each read replaces the video's points in `retention_curves` (one row per point of `elapsed_video_time_ratio`, with `audience_watch_ratio` and the read's time) and its row in `retention_curve_reads` (migration 0038). A video too small for YouTube to return a curve gets its `retention_curve_reads` row and no points, so it is not read again until it is due. YouTube's relative retention performance is not stored (ADR 0004). A free channel reads nothing, and an ended one keeps what it holds until the history purge. Any refusal ends the run and keeps what is stored; a Google failure is reported to GlitchTip with the channel ID only, and a reserved quota or a revoked connection is not.

The stored curves are compared on the retention page (#951), `/app/retention`, which the sidebar's "Retention" link after "Audience" opens for every channel. `GET /api/channels/:channelId/retention-curves?ids=<id>,<id>` answers up to 5 of the channel's videos, in the order `ids` lists them, each with its id, title, length and publish time, `readAt` (when Google answered the read that stored its curve, or null for a video the refresh has not read yet) and its points from `retention_curves`, earliest first, each `elapsedVideoTimeRatio` and `audienceWatchRatio` and no relative retention performance (ADR 0004), none for a video read with no curve. The answer also carries `unread`, how many of the channel's published uploads have no `retention_curve_reads` row yet, so the page shows a note while the backfill fills, or null for an ended channel, which the refresh no longer reads, so the page shows none. With no `ids` it answers no curve and the count. An empty or malformed list, more than 5 ids (duplicates counted, then collapsed) or `ids` sent twice answers 400 `invalid_ids`; a video the channel does not hold, 404 `video_not_found`; a channel whose history is not readable (free, or ended past its purge date), 403 `sort_without_history`, the code the Pro sorts use, before any Google request; a channel the user does not hold, 404 `not_connected`. It spends no Analytics query: its one Google read is the channel's uploads, cached as the video list's. The page lists the channel's videos over their lifetime, by format and newest first, oldest first or by average viewed in either direction, a page at a time, and the creator ticks up to 5 to draw on one chart, each line in its pick's colour and each labelled in the legend with its title and its read date. One hover card, and the arrow keys, read every curve at the same share of the video. The picks live in the address as `curves=<id>,<id>`. A pick the channel no longer holds, such as a video deleted since the address was bookmarked, is dropped from the address, and the rest are drawn.

A completed deletion request keeps its reason, the memberships it ended, its request time and its completion time, and no channel id. Each day at 03:00 UTC the `deletionRequestRetention` job deletes the requests completed more than 24 months ago, the same window as the deletion log (#23). The system scope's delete policy on `deletion_requests` (migration 0012) admits only those rows, so an open request is never deleted.

An account deletion cancels the user's Stripe subscription at once and refunds the unused part of the period (#784, ADR 0024). A disconnect or a revocation at Google cancels and refunds nothing: it deletes the channel's data as before, and frees the channel's slot at once, since a pick counts only while its user still owns the channel, so the subscription keeps paying for the user's other channels. "Delete me" never waits on Stripe, so the user and their channels still go on time when Stripe is down. Before it deletes the user row, which takes the user's `user_subscriptions` row with it, `DELETE /api/me` reads the user's subscription through the `entitlements` package and, when its status is any but `canceled` or `incomplete_expired`, writes a row in `account_cancellations` (migration 0041) and enqueues a `cancelAccountSubscription` job now and an `accountCancellationAlarm` job at 12 hours, in the deletion's transaction, with the cancellation's uuid as their data. That row holds the Stripe subscription ID and its time, and no user id, since it outlives the user; the user scope writes it only for its own subscription and cannot read it back, and only the system scope reads and deletes it. The job, in the system scope, cancels the subscription with `prorate` and `invoice_now` false, so Stripe adds no proration credit to the customer's balance, then refunds the latest paid invoice's `amount_paid` times the share of the period left after the subscription ended (Stripe's `ended_at`, not its `canceled_at`, which a cancellation at period end leaves at the time of the request), rounded to the cent, against that invoice's PaymentIntent. Then it deletes the row, so no Stripe ID outlives a completed cancellation. A user with no live subscription writes no row and makes no Stripe call. A Stripe error fails the job, which is reported to GlitchTip and retried 11 times an hour apart; a retry cancels nothing already canceled and refunds nothing already refunded, found by the refund's `stillstats_cancellation_id` metadata. A cancellation still pending when its alarm runs at 12 hours is reported to GlitchTip as "A subscription cancellation is still pending 12 hours after its account deletion", with the cancellation's id only. Under Managed Payments, Link tells the customer of the refund, which includes the tax they paid, and Stillstats sends no email. The channel deletion's `cancelSubscription` job and its `subscription_cancellations` table (migration 0032) stay only to drain a row the previous release's worker writes during the deploy; this release writes none, and the remove release drops them.

`TOKEN_ENCRYPTION_KEYS` holds the token vault's AES-256-GCM keys as `version:base64key` pairs separated by commas, for example `1:<32 random bytes in base64>`. New tokens are sealed under the highest version. To rotate, append a higher version and keep the older keys: each connection is resealed under the new key the next time the vault uses it. Generate a key with `openssl rand -base64 32`.

`GOOGLE_IDENTIFIER_KEY` is the HMAC key of each connection's Google identifiers: the Google subject, and the refresh token's first 16 characters and double SHA-512 hash. A Google security event (RISC) finds its connection by them, and the database never stores the identifiers themselves. Generate it with `openssl rand -base64 32`, and never change it: a new key leaves every stored connection unfindable by a security event until its next consent.

Stripe's webhook posts to `POST /api/stripe/events`, with no session, and the route exists only when the tip's settings, `STRIPE_PAYMENT_LINK_URL`, `STRIPE_WEBHOOK_SECRET` and `STRIPE_PAYMENT_LINK_ID`, or Pro's are set; both read the one `STRIPE_WEBHOOK_SECRET`. The API verifies the `Stripe-Signature` header against the raw body with `STRIPE_WEBHOOK_SECRET`, through Stripe's own Node library, which only the API and the worker import. A missing or wrong signature, a body changed after signing, or a timestamp more than five minutes old answers 400 and records nothing. A verified event answers 200, unless writing it fails, which answers 500 so Stripe delivers it again. Stripe sends `checkout.session.completed` for every Checkout Session on the account, a Pro Checkout's included, so a session whose `payment_link` is not `STRIPE_PAYMENT_LINK_ID`, the Stillstats Payment Link's `plink_` ID, records nothing, reports nothing and answers 200, whatever its payment or `client_reference_id`. A paid `checkout.session.completed` from the Stillstats link records a tip for the user its `client_reference_id` names, once per Checkout Session, so a repeated delivery changes nothing. A newly recorded tip, and only that, sends `revenue` to OpenPanel with `__revenue` (the session's `amount_total`, in cents) and `currency` (`usd`), so a repeated delivery sends nothing. OpenPanel counts revenue only from an event named `revenue` with an integer `__revenue`, the shape its SDK's `op.revenue` sends. Any other event type or an unpaid session records nothing. A paid Stillstats session with no `client_reference_id` records nothing and reports to GlitchTip with the Checkout Session ID only. One whose `client_reference_id` names no user, such as an account deleted while Stripe's page was open, records the tip with no user, sends `revenue` once, and reports to GlitchTip with the Checkout Session ID only. A page loaded on a screen with no budget, and one on which no budget screen ever shows, sends no LCP; INP is each screen view's worst interaction, skipping one per 50, sent when the screen changes again after that view (the browser reports the input that left a view only once the next screen has painted), or when the page is hidden. Both are read with the browser's own `PerformanceObserver`. It carries no ID and no address
- `answer_shown`, with the budget `screen`, the `trigger` (`load`, `filter`, `sort`, `page` or `window`), the `filter` changed (`format`, `visibility`, `trafficSource` or `minImpressions`) with the `filter` trigger only, the `window` (a custom range is `custom`, with no dates), the `cache` (`hit` or `miss`, the answer's `fromCache`, or `stored` for the retention comparison's curves) and `ms`, the wait in whole ms: from navigation start for the page's first answer, else from the input to the render of its answer. The channel screen times its video list, and the retention comparison its curves on a load and its picker's list on a sort, page or format change; a pick, a chart mode, a refusal and a read again with no input send nothing. It carries no ID and no address

The feedback form posts each message to `POST /api/feedback` as `{"type":"idea","text":"...","screen":"audience","appVersion":"2026.11.15"}`, with `"appVersion"` only when the build has a version, the one the client settings answer gives, and `"replyTo"` only when the creator ticks the reply box. The API stores the version as sent. The types and screens live in `packages/api-types/src/feedback.ts`, which the web app imports. The screen is `extension` when the form opens from the extension popup's "Send feedback" link, at `/app/feedback?screen=extension`. A signed-out request answers 401. Past 10 messages in 24 hours from one account, counted in the database and whatever the body, the API answers 429 `rate_limited` and saves nothing. Then, in this order, a body that is not a JSON object answers 400 `invalid_feedback`, an unknown type `invalid_feedback_type`, a text empty after its control characters (all but line breaks and tabs) are removed and it is trimmed, or longer than 5,000 characters, `invalid_feedback_text`, an unknown screen `invalid_feedback_screen`, a version that is not the app's CalVer (`YYYY.M.D` on a real day, or `YYYY.M.D.N`, with no leading zero) `invalid_app_version`, and a reply address that is not a valid email address or is longer than 254 characters `invalid_reply_address`. Any other key is ignored. A saved message answers 201 with no body. Once it is saved, the API emails Nick through Cloudflare Email Service: one email per message, holding its type, the time and the link to the admin screen, never the text, the reply address or the account. The send runs after the save, and the answer is 201 whether it succeeds or fails; a failed send is reported to GlitchTip with the message's ID and no text. With the four email settings unset, as on staging, nothing is sent (see `docs/deploy.md`).

Each day at 03:00 UTC the `feedbackRetention` job deletes the feedback messages marked "Done" more than one year ago, the limit the privacy policy publishes. The system scope's delete policy on `feedback_messages` (migration 0026) admits only those rows, so an open message is never deleted, and the system scope reads, inserts and updates none.

Nick reads the messages on the admin feedback screen, `/app/admin/feedback`, which nothing in the web app links to. It reads `GET /api/admin/feedback?page=N&open=true`, which answers `{"messages":[...],"pageCount":N}`, 50 messages to a page, newest first, each with its ID, type, text, screen, app version, reply address, time sent and "Done" time, and no account ID; `open=true` keeps only the messages not yet "Done", and a malformed `page` or `open` answers 400 `invalid_query`. `PUT /api/admin/feedback/:id/done` marks a message "Done", keeping an earlier time, and `DELETE /api/admin/feedback/:id/done` clears it; each answers the message as it now stands, and an unknown ID answers 404 `not_found`. The routes run in the admin scope, which the API enters only for a signed-in user whose ID is in `ADMIN_USER_IDS` ([the deploy guide](docs/deploy.md#dokploy)). To anyone else, signed out included, every path under `/api/admin/` answers 404 `not_found`, as an unknown route does, and the screen shows its not-found page.

The Studio extension sends its events through the API, never to OpenPanel itself, so its host access stays at Studio and the API (ADR 0008). It posts each one to `POST /api/events` as a flat JSON object, such as `{"name":"extension_surface_shown","surface":"card","ms":1200,"fromCache":false}`, and the API relays it to the same OpenPanel project. The names and values live in `packages/api-types/src/events.ts`, which the extension imports. A signed-out request answers 401. An unknown name, a missing or unknown value, or any other key answers 400 `invalid_event` and sends nothing. The relay accepts `ms` and `fromCache` on `extension_surface_shown` only, both together: `ms` a whole number of 0 or more, `fromCache` true or false. It also accepts that event with its surface alone, as an extension from before the timing still sends it. Past 60 events in one clock minute from one user, whatever the body, the API answers 429 `rate_limited` and sends nothing. The surface is one of the three Studio surfaces, `card` (the latest video card), `content_list` (the Content list) or `analytics` (a video's analytics page), or the four public page surfaces on www.youtube.com, `channel_page` (the channel's Videos, Live and Home tabs), `watch_page` (the view count under a watch page's title), `feed` (the home feed, search results and the watch page's sidebar) or `shorts` (the channel's Shorts tab and the Shorts player). The extension sends these, one line each:

- `extension_installed`, once per install, on the first read after install that shows the creator signed in: the install's own read when the creator is already signed in, otherwise the first later read from a surface or the popup. Its time in OpenPanel is that read, not the install, so the raw install count comes from the Chrome Web Store and Firefox Add-ons dashboards. Until it is sent, the background holds it in the extension's IndexedDB, through an idle background and a browser restart, and a send the relay does not accept stays held for the next signed-in read. In Firefox it is sent only while the creator allows usage events: an install with them declined holds it too, and sends it on the first signed-in read after the creator allows them in about:addons.
- `extension_surface_shown`, with the surface the extension added its numbers to, `ms`, the time in whole milliseconds from the moment the pass that found the surface's element was due, or the moment the extension first saw the element when that came later, to its figure showing (a pass that ran on the new URL before the extension learned of the navigation counts for that navigation), and `fromCache`, true when every answer the figure was drawn from came from the API's cache or the extension's 30-second keep, or when the figure stayed up from an earlier navigation, so no request left the browser. A surface that shows only a line (the sign-in line, the connect prompt or a refusal) sends no shown event, so no time. It carries no channel, video or user ID
- `extension_surface_missing`, with the surface whose selector found nothing on the page
- `extension_sign_in_clicked`, with the surface whose sign-in line the creator clicked, sent once the creator is signed in, since the relay answers a signed-out request 401. Clicks on one surface before then send one event.
- `extension_connect_channel_clicked`, with the surface whose connect prompt the creator clicked
- `extension_web_app_opened`, with the surface the creator opened the web app from: the analytics page's "View this video in Stillstats" link, or a refusal line's link
- `extension_popup_web_app_opened`, when the creator opens the web app from the popup's "Open Stillstats" link
- `extension_popup_feedback_opened`, when the creator opens the feedback form from the popup's "Send feedback" link
- `extension_popup_sign_in_clicked`, when the creator who clicked the popup's sign-in link is signed in
- `extension_youtube_access_granted`, when the browser grants YouTube access, from the popup's toggle or the browser's own extension settings
- `extension_youtube_access_removed`, when the browser removes YouTube access, from the popup's toggle or the browser's own extension settings

The API reads `OPENPANEL_API_URL`, `OPENPANEL_CLIENT_ID` and `OPENPANEL_CLIENT_SECRET` at runtime for the relay. That client ID is the project's write client, and it is never the one `GET /api/client-settings` answers the web app and the site: they send with the project's website client, `OPENPANEL_WEB_CLIENT_ID`, and no secret. OpenPanel's server-side tracking needs the project's client secret, which only the API holds. With any one of the three unset, the relay sends nothing and still answers 204. The relay forwards the caller's user agent and IP (the `CF-Connecting-IP` Cloudflare sets, never a client-chosen `X-Forwarded-For` entry) and no profile id, so OpenPanel ties an extension event to a device the way it ties the web app's, and no user id leaves the API. A relay OpenPanel refuses or never answers is reported to GlitchTip and still answers 204. The product sends two server events of its own, and each forwards no user agent and no IP and carries no profile id, so OpenPanel files it as a server event with no session. The API sends `revenue` from the Stripe webhook, for a tip and for each paid invoice of a Pro subscription, since Stripe's request is not the creator's browser; an OpenPanel that refuses it or never answers is reported to GlitchTip, and the webhook still answers 200. The worker sends `active_users_counted` once a day at 00:15 UTC, with `dau`, `wau` and `mau` for the UTC day that just ended, stamped at noon UTC on that day, so the point sits on that day in any project time zone from UTC-12 to UTC+11. An OpenPanel that refuses it or never answers is reported to GlitchTip and fails the job, which pg-boss retries six times, five minutes apart, and each retry counts the same activity days.

The Studio extension lives in `apps/extension` (ADR 0010), built with WXT from one codebase for Chrome and Firefox, both Manifest V3. `pnpm build` writes `apps/extension/.output/chrome-mv3` and `firefox-mv3`, which call `https://stillstats.com`. `pnpm --filter @creator-analytics/extension build:dev` writes `chrome-mv3-dev` and `firefox-mv3-dev`, which call the local API at `http://localhost:3000` and add it to the host access. `pnpm build:extension:staging` writes `chrome-mv3-staging` and `firefox-mv3-staging`, which call `https://staging.stillstats.com`, ask for host access to Studio and staging only, and send a Cloudflare Access service token as the `CF-Access-Client-Id` and `CF-Access-Client-Secret` headers on every API request. The build reads the token from `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` in the local env (Development, above), and fails without either. Only the background script calls the API (`apps/extension/src/product-api.ts`), with the creator's stillstats.com session cookie. Installing the extension opens its first-run page, which says what the extension reads, what it sends and what Stillstats keeps, and links the privacy policy. An update never opens it. The popup asks the background script for the channels and shows the sign-in state. A signed-in popup, with or without a channel, also shows a "Send feedback" link, which opens the web app's feedback form in a new tab with the screen `extension`. When the creator withholds site access in Chrome or Firefox, the popup asks for it with "Allow access" before it reads anything. In Chrome 133 and later the extension also asks for withheld site access beside the extensions icon, on a Studio or stillstats.com tab. The popup's "Show engaged views on youtube.com" toggle, off by default, asks the browser for YouTube access, an optional host permission for www.youtube.com that the install never asks for (ADR 0016). While it is granted, the background registers the youtube.com content script and injects it into the www.youtube.com tabs already open, and it unregisters the script when the creator turns the toggle off or removes the access in the browser's settings. On www.youtube.com the background reads each held channel's uploads through the video list, and the tab matches the page's videos against them, so no video id from the page is sent. On that removal the background also tells the open tabs, so a www.youtube.com tab already running the script stops and takes its pills down without a reload, and while YouTube access is removed the background passes no request from a www.youtube.com tab on to the API. A www.youtube.com page the browser held in its back/forward cache misses that message, so when the browser restores it, the page asks the background whether YouTube access is still granted and takes its pills down if it was removed meanwhile. The Firefox build declares the session cookie as required `authenticationInfo` data, the video ids it reads from Studio's links as required `websiteContent` data, and the usage events as optional `technicalAndInteraction` data, and sends no usage event when the creator declines it.

The store screenshots in `apps/extension/store-assets` are the real built extension on saved Studio pages, showing the homepage's made-up channel, never a creator's (ADR 0009). Retake them with `pnpm --filter @creator-analytics/extension screenshots`, which needs Google Chrome (in `/Applications`, or at `CHROME_PATH`): it builds the extension, installs the build in headless Chrome, opens the pages in `apps/extension/test/fixtures/studio` at their Studio addresses with Studio's own stylesheet and the creator's data swapped for the sample channel, and answers the background's reads of stillstats.com from a stub in `apps/extension/test/screenshot/`. It writes five PNGs of 1280 by 800, the size both stores ask for, with no "Sample data" label, and the Chrome Web Store's small promo tile, 440 by 280: the S of the favicon on the visual system's accent colour, with no text. To retake only some of them and leave the rest as they are, name them: `pnpm --filter @creator-analytics/extension screenshots 4-popup.png`. The script and the images sit outside `public/`, so the extension's build holds none of them.

The site (`apps/site`) reads `VITE_OPENPANEL_API_URL` at build time and the client ID at load, as the web app does. It sends page views, `sign_in_clicked`, which carries `source: 'thumbnail-preview'` from the tool page's sign-in band and no `source` from the homepage, and, from the tool page, the thumbnail preview tool's `thumbnail_load` (`slot`, `mode`, `detected`, `source`), `thumbnail_title_entered` (`slot`), `thumbnail_mode_switch` (`from`, `to`), sent on a press of the Format control or a mismatch notice's switch that changes the mode, `thumbnail_grayscale_toggle` (`on`), sent on a press of the Preview control that changes the preview, and `thumbnail_focus_toggle` (`on`, `surface`), sent each time focus mode opens or closes, none of which carries an image, a file name or a title. From the homepage it sends `upgrade_link_clicked` with `source: 'homepage'` on a click of the Pro card's "Subscribe" (creator-analytics#907), the web app's own event for its sidebar item, with no plan, price, channel or account ID. "Subscribe" is a plain link to `/app/upgrade`, signed in or not: the web app opens the upgrade screen there for the first channel, signs a signed-out visitor in first with its own sign-in screen, and takes a new visitor through the connect step too, landing on the upgrade screen for the channel just connected. Every site page asks `GET /api/me` once on load; signed in, the header shows the avatar, a link to `/app`, and the homepage's and the tool page's "Sign in with Google" button becomes "Open your dashboard", with no new event. The API serves the site at `/` and the web app under `/app`, and its image refuses to build without `VITE_OPENPANEL_API_URL`, because without it the OpenPanel SDK sends to openpanel.dev's cloud (ADR 0007).

The homepage screenshot, `apps/site/public/app-screenshot.webp`, is the real web app showing a made-up channel, never a creator's (ADR 0009), and the homepage captions it "Sample data". Retake it with `pnpm --filter @creator-analytics/site screenshot`, which needs Google Chrome (in `/Applications`, or at `CHROME_PATH`): it builds the web app without the OpenPanel and GlitchTip hosts, serves it from a stub API that answers with the sample channel in `apps/site/test/screenshot/`, and saves `/app` from headless Chrome at 1280 by 1232 CSS pixels and a device scale of 1.5, a 1920 by 1848 WebP that Chrome encodes itself at quality 90. The stub sits under `test/`, so the API image and the site's build hold none of it.

Error tracking goes to a self-hosted GlitchTip through Sentry's SDKs: `@sentry/node` in `packages/reporter` for the API and the worker, and `@sentry/react` in the web app. The API and the worker read `GLITCHTIP_DSN`. The web app reads `VITE_GLITCHTIP_DSN` at build time. With the DSN unset, a process reports no error to GlitchTip. Every report carries the environment, `production` or `staging`, and the version as its release: the API and the worker read both at start, and the web app from `GET /api/client-settings` at load. The version is the newest app release note in the build; with none yet, a report carries no release.

The site's build and the web app's build both write one content security policy into every page they write, as a `<meta>` tag (`packages/visual-system/src/content-security-policy.ts`, through the `contentSecurityPolicy()` plugin in `packages/visual-system/src/vite.ts`), because only the build knows the OpenPanel and GlitchTip hosts. The one exception is a tool page, a page in the site's `tools/` folder such as `/tools/thumbnail-preview`, whose `img-src` adds `blob:` for the object URLs the tool makes from a creator's own files, which never leave the browser (ADR 0021); every other directive is the same. Styles and fonts load from the page's own origin only, and scripts from that origin and `https://www.youtube.com`, the host of YouTube's IFrame Player API and the player script it injects; the only frame is YouTube's player, from `https://www.youtube-nocookie.com` (`frame-src`). The web app loads either only on a video's detail screen that holds the player, as the screen opens (ADR 0019 and ADR 0020), and `apps/web/src/youtube-player.ts` is the only code that talks to the player. Images load from the page's origin and YouTube's `*.ytimg.com` hosts (the web app's thumbnails; a private or unlisted video's comes from a numbered host such as `i9.ytimg.com`), and a page connects only to the API and the OpenPanel and GlitchTip hosts. The policy allows no inline script, so the web app's theme script, which sets `data-theme` from the browser's copy of the theme before the first paint, is a file from the page's own origin: the build bundles `apps/web/src/theme-script.ts` on its own into `assets/` and loads it as a classic script, the only script ahead of the stylesheet in the head (`apps/web/theme-script-plugin.ts`). The web app's build reads `VITE_YOUTUBE_IFRAME_API_URL` for the IFrame API script's address, and only the browser walk's build sets it, to its fake player served from the page's origin (`apps/site/test/screenshot/fake-youtube-iframe-api.js`); unset, as in every deployed build, it is `https://www.youtube.com/iframe_api`. A change to `VITE_OPENPANEL_API_URL` or `VITE_GLITCHTIP_DSN` needs a new build for the policy to follow. The dev servers serve the pages without the policy.

Every event passes a scrubbing hook (`packages/reporter/src/scrub.ts`) before it leaves the process, and every line the reporter's logger writes passes the same rule. The rule is an allowlist: a context value leaves only when it is an internal id (a uuid) or sits under an allowed key such as `status` or `port`. Everything else is dropped, so a new field stays out of GlitchTip and out of the logs until someone adds its key to the list on purpose. Tokens, YouTube channel ids and query strings are masked in messages, and so is every number but an HTTP status (100 to 599), because a number in a message can be a creator's analytics value. A uuid in a message is kept whole. The request's headers, cookies and body never leave. The SDK records no session, because GlitchTip accepts no sessions. A trace of an API request leaves only with `GLITCHTIP_TRACES_SAMPLE_RATE` set, and then through a stricter trace scrubbing hook that keeps no internal id either: its name is the method and the route's pattern, and it carries only the window, the filter names, the cache result, the status and its timings (ADR 0023). A request answered 401 to 404, or with a redirect other than 300 and 304, sends no trace: the SDK's default filter drops it. So a signed-out request and the `not_connected`, `video_not_found`, `consent_missing`, `not_monetized` and `not_owner` refusals are not in GlitchTip's p50 and p95.

Each deployed image runs its package's `start` script (`pnpm --filter @creator-analytics/api start` and `pnpm --filter @creator-analytics/worker start`), never its own `node` command, so a flag a package needs at start lives in one place.

A merge to `main` deploys staging: CI builds and smoke-runs the API and worker images, pushes them to GHCR, runs the migrations against the staging database as the migration role, moves the `staging` tag, then calls the staging Dokploy deploy webhooks. A published GitHub release deploys production: the release workflow checks the tag against the newest release note, runs the production migrations, moves `latest`, then calls the production webhooks. A failed migration stops the deploy. The rollback workflow puts an earlier release's images back on production by its version, with no migration, and refuses to go back past a release whose note sets `removes: true`. `docs/deploy.md` holds both paths, the GitHub Environments and their secrets, and the Dokploy setup.

Database roles:

- `app_migrator` owns every table and runs `pnpm --filter @creator-analytics/database migrate` with `MIGRATION_DATABASE_URL`. It is provisioned by hand with `LOGIN CREATEROLE`, because the migrations create the other four roles.
- `app_web` (the API) and `app_worker` (the job worker) are created by the migrations without `LOGIN`. Each process logs in as its own login role that is a member of one of them.
- `app_claim` is created by the migrations without `LOGIN`, and no login role is a member of it. It owns the `claim_channel` function only, which is the one path that writes `channels` and `memberships` for a user.
- `app_roster` is created by the migrations without `LOGIN`, and no login role is a member of it. It owns the `connection_roster` function only, which is the one path by which the system scope reads the connection roster: each active connection's channel id, Google subject HMAC and connection time. It holds SELECT on the roster columns only, and on no token.
- A process refuses to start when its login role is a superuser, has `BYPASSRLS`, or can act as a table owner.
- The migrate step also installs or upgrades pg-boss in the `pgboss` schema, creates every queue in `jobNames` (`packages/database/src/jobs.ts`), and grants `app_web` and `app_worker` the rows of pg-boss's tables. A login role that created pg-boss's tables would own them and fail the check above, so no process but the migration changes that schema. A new job adds its name to `jobNames`, and the next migrate creates its queue. A scheduled job also adds its cron to `jobSchedules`, which the migrate step writes as a pg-boss schedule.
- New schema: declare a table that holds a channel's rows with `channelOwned`, then run `pnpm --filter @creator-analytics/database generate`.
- `packages/database` depends on `kysely` without using it. Better Auth brings `kysely`, and `drizzle-orm` lists it as an optional peer, so without it pnpm installs a second copy of `drizzle-orm` for the API.
