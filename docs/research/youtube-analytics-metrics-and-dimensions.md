# YouTube Analytics metrics and dimensions the app does not read yet

The question, from creator-analytics#159: what other stats could the app show? This lists what Google's YouTube Analytics API offers a channel owner for the channel's own reports, marks which of it the app reads today, and ranks five to consider first. Origin: Nick's inbox note of 2026-10-10.

Read on 2026-10-12. "Read today" is the code at `024930599b6d27bcc211ff6be4b8a7ba8e421601`, the base of the creator-analytics-159 branch. A file named in the tables is in `packages/youtube-gateway/src/reads/`. A read that goes through a helper (`channel-metrics.ts`, `video-metrics.ts` or `one-video.ts`) is listed under the file that defines its query, not the helper. `channel-snippet.ts` and `uploads.ts` read the Data API and are left out.

## How to read the tables

- **Scope.** Only what a channel can ask of its own reports (`ids=channel==MINE`). Google's content-owner items are left out: the `channel`, `claimedStatus` and `uploaderType` dimensions, and the `CAMPAIGN_CARD` traffic source value. Playlist reports are kept, because the channel reports page lists them for a channel.
- **Report combinations** are named as the channel reports page names its sections. Video reports: Basic stats, Time-based, User geography, Playback details, Playback locations, Traffic sources, Device type and operating system, Viewer demographics, Engagement and content sharing, Audience retention, Concurrent viewers (for livestreams), Top videos. Playlist reports: Basic stats, Time-based, User geography, Playback locations, Traffic sources, Device type and operating system, Viewer demographics, Top playlists. Then Membership cancellations and Ad performance by ad type. Each report is a set of dimensions, metrics and filters. The page says an unsupported combination gets a 400 ("The query is not supported"), but its tables are not the whole of what Google accepts: the app's per-format channel-wide query, with no dimension and a `creatorContentType==` filter, is in no report table. `channel-metrics.ts` records only that a live check on 2026-10-08 refused the uppercase values Google's docs list in that filter, such as `SHORTS`; no check of the lowercase filter the app sends is recorded.
- **Monetary scope.** "Yes" when the channel reports page marks the metric with an asterisk, "monetary metrics that require this scope and monetization status": the `yt-analytics-monetary.readonly` scope, and a channel in the YouTube Partner Program, or Google answers 403. The app holds that scope only with revenue consent.
- **Cost of one more read.** The Analytics API counts queries, not units (`read-definition.ts`, `GoogleCalls.analytics`), against "Queries per day" on the Cloud Console quotas page, 100,000 a day with the last 10% reserved (`youtube-gateway.ts`). "0 extra queries" means the metric fits the report of a query the app already sends, named in the cell, so it rides along. "1 query per read per cache window" means a new query, cached for 6 hours like every read today: per channel for a channel-wide read, per video for a one-video read. A "0 extra queries" claim rests on the channel reports page for the whole-channel query with no filter, the one-video queries with a `video==` filter, and the reads by `video`. It does not for one format of `channel-totals.ts` and `channel-revenue.ts`: when a format is chosen, `channelMetrics` in `channel-metrics.ts` sends no dimension and a `filters=creatorContentType==<format>`, a shape the page never lists, since it names `creatorContentType` only as a dimension. So a metric riding on those two reads costs 0 extra queries for every format, but for one format the cost is unproven until a live check shows Google takes that metric in that shape; those cells say "one format unproven". Live checks of the query shapes the app sends are recorded in the comments of some read files (`video-daily-rows.ts`, `video-daily-series.ts`, `video-daily-revenue.ts`, `video-daily-revenue-rows.ts`, `video-revenue.ts`, `video-window-revenue.ts`, `video-content-types.ts`, `channel-revenue-by-format.ts`) and in the headers of `apps/api/src/video-detail.test.ts`, `video-list.test.ts` and `video-revenue.test.ts`. None is recorded for the channel-wide queries of `channel-totals.ts`, `channel-daily-series.ts`, `channel-revenue.ts` and `channel-daily-revenue.ts`, with no dimension or by `day`, so the cells that name those reads rest on the channel reports page alone. `video-revenue.test.ts` records the video list's revenue queries with the three revenue metrics as a shape no live check has covered. Each new metric gets a live check in the shape the app sends it before it is built.
- **Legacy items** keep a row so the list matches Google's page, and are never ranked.

## Five to consider first

The rule: the item measures how the channel's own viewers respond (ADR 0009); it is not a benchmark, a grade or an attention trick (ADR 0011); and the screen shows it as YouTube returns it, or with simple arithmetic at most (ADR 0013). Then cheaper first: no new scope, then 0 extra queries, then 1. Then what fills a gap on today's screens, then what a small creator acts on. Geography is creator-analytics#158's, so `country` is not ranked.

1. **`subscribersLost`.** The video list and the video detail show subscribers gained today, and this is the other half: subscribers gained less subscribers lost is the subscribers a video or a window netted, a subtraction ADR 0013 allows. It rides along in the queries the video list and the video detail already send, with no new scope. Per video it counts only unsubscribes from that video's watch page, which the column's note has to say.
2. **`shares`.** A share is a viewer passing the video on, the most direct sign of a response the app does not show yet. It fits the same queries at 0 extra cost, and `sharingService` can follow later, at 1 query, to show where the shares went.
3. **`comments`.** A creator answers comments, so a count by video and by window says where the conversation is. 0 extra queries, no new scope, and a sort by it is a sort, not a rank (ADR 0013).
4. **`likes`.** The commonest response a viewer gives, at 0 extra queries in the same reads. It is shown as a count; a likes-per-view ratio would be a division of the video's own numbers, like RPM, and stays simple arithmetic, but it is not needed for the first version.
5. **`averageViewDuration`.** Beside the average percentage viewed the screens already show, the minutes and seconds a playback lasts, as YouTube computes it, which is the figure a creator compares with the video's length. 0 extra queries in the video detail's read and in the video list's read for a calendar window. In a window after publish the list adds each video's days up, and an average duration does not add, so the list has none there, as with average viewed. Like average view percentage under ADR 0013, it is a ratio YouTube computes, so it is shown as YouTube returns it and never averaged or combined.

Next after these, each at its own cost: `stoppedWatching` (0 extra queries, in the audience retention read, to mark where viewers leave), and `insightTrafficSourceDetail` for YouTube search (1 query a video, the search terms that brought viewers; it shows how viewers found the video, and stays clear of the keyword scores ADR 0009 retires). Not recommended on this rule: `grossRevenue`, `cpm`, `playbackBasedCpm`, `adImpressions`, `monetizedPlaybacks` and `adType` measure the advertiser's side, not the viewers' response, and the annotation metrics are legacy.

Any new read changes what the product reads from YouTube, so the privacy policy, which creator-analytics#61 brings up to date with what the product reads, changes with it.
